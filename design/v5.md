# v5 — same bot as a Conductor Agent (code path)

PRD v5. The same wealth-advisor bot, written as ~30 lines of Python with the Conductor Agents
SDK (`conductor.ai.agents` `Agent`, `AgentRuntime`, conductor-python 2.0.0), pointed at
the Ollama model (`CONVO_LLM_PROVIDER`/`CONVO_LLM_MODEL`). Run it twice with one `session_id`
and it remembers. Deploy it, then call it from a workflow with an AGENT task. Every run is a Conductor execution.
No new Python dependencies.

## 1. Layout (all under `convo-agent/v5/`, owned by v5)

```
v5/__init__.py
v5/agent.py        # build_agent() -> Agent "wealth_advisor" (+ optional get_portfolio tool); the showcase file
v5/memory.py       # load_history(conductor, session_id, prev_execution_id) -> (history, restored, source)
v5/turn.py         # run_turn(session_id, message, prev_execution_id="") -> S4-shaped dict (the one code path)
v5/chat.py         # CLI: python -m v5.chat --session S [--prev ID] "message"   (and --interactive)
v5/probe.py        # python -m v5.probe -> JSON report of what works on this server (section 3)
v5/worker.py       # python -m v5.worker --port 8751: runs SIMPLE task convo_v5_agent_run + /healthz
v5/tools.py        # get_portfolio(client_name) tool, reads v5/data/portfolios.json
v5/data/portfolios.json   # own copy (Jane Doe, John Smith, ...); versions never share files
v5/conductor/workflows/convo_v5_agent_turn.json    # AGENT task (or fallback SIMPLE, section 3)
v5/conductor/workflows/convo_v5_chat_turn.json     # S4 adapter so v2.server works unchanged
v5/conductor/workflows/convo_v5_chat_history.json  # S4 history companion
v5/conductor/tasks/convo_v5_tasks.json             # convo_v5_agent_run task def
v5/smoke.py  v5/manifest.json  v5/README.md  v5/tests/
```

## 2. The code path (what the README shows)

`agent.py` is the showcase file. Keep it short:
`Agent(name="wealth_advisor", model=f"{provider}/{model}", instructions=PERSONA, tools=[get_portfolio])`.
`turn.run_turn` is the only place that runs it. Front doors (CLI, web, smoke) call `run_turn` or the
workflows, nothing else. `run_turn` returns S4 keys plus extras:
`{reply, history, executionId, sessionId, restored, memorySource, agentMode, toolCalls}`.
- `memorySource` ∈ `"sdk-session"` (the SDK's own session lookup found history), `"explicit"`
  (our fallback loaded it by execution ID), `"none"` (fresh start; the reason is in `memoryNote`).
- `agentMode` ∈ `"server"` (AGENT task / server-side agent ran) or `"local"` (fallback, section 3).
`history` follows S4: user/assistant pairs only, at most 20 entries, appended in pairs. `executionId` is the agent run's
Conductor workflow id, so the UI link works.

## 3. Verify-first, then a reported fallback (decision)

The PRD says the SDK's session lookup runs in the client, uses search (index lag), and
**silently** returns nothing on error. On OSS the AI flag / AGENT task may be missing too.
`v5/probe.py` checks each point and prints `{"aiEnabled", "agentTask", "sdkSessionMemory", "notes"}`.
The README records the result on a local Conductor OSS server. Rules:

1. **Memory never comes only from the SDK.** `memory.load_history` always runs before the agent:
   if `prev_execution_id` is given, `get_workflow` it and accept only if COMPLETED, same
   `sessionId` (input or correlationId), else `search_by_correlation(session_id)` newest COMPLETED
   v5 run. It then passes the history into the agent's prompt explicitly (as prior messages, or one
   "Conversation so far:" block if the SDK has no message-list input). If SDK session memory also
   works, set `memorySource="sdk-session"`. Otherwise use `"explicit"`. Search lag is handled by trying
   `prev_execution_id` first. The CLI and web always pass it.
2. **AGENT task.** `convo_v5_agent_turn` is written with the AGENT task
   (`agentType: conductor`, `name: wealth_advisor`, `prompt`, `sessionId`). If the probe shows
   the server rejects AGENT (unknown task type or AI flag off), the registrar step in
   `v5/probe.py --write` swaps the file it registers for the variant where that one task is SIMPLE
   `convo_v5_agent_run` with the same inputs. That task is executed by `v5.worker`, which calls
   `turn.run_turn` (the Agent run locally via `AgentRuntime`). Output is the same, and `agentMode="local"`
   is reported. Do not edit the platform registrar: the probe registers the variant itself with
   `Conductor.register_workflow` after `convo.sh start` has registered the default.
3. Agent run fails → `run_turn` raises; workflow FAILED; CLI exits 1 with the reason. Never a
   reply that pretends to remember.

## 4. Workflows

- `convo_v5_agent_turn` input `{sessionId, prevExecutionId, message, llmProvider, model}`;
  steps: Get Workflow(prev, optional) → JQ build (same S4 rule as v1: history from a COMPLETED,
  same-session prior run) → AGENT (prompt = JQ-built prompt with history) → JQ save. Output S4 + `agentMode`.
- `convo_v5_chat_turn` = Sub Workflow `convo_v5_agent_turn`, passing S4 input/output through, so
  `python -m v2.server --version v5 --port 8750 --title "Advisor as a Conductor Agent"` serves the
  chat unchanged (S5). `convo_v5_chat_history` = Get Workflow + JQ (S4 companion).

## 5. Manifest / processes

`processes`: `web` (v2.server, 8750, `/healthz`), `worker` (`python -m v5.worker --port 8751`,
`/healthz`). It runs always: it is cheap, and it also serves the local mode. `links`: Chat
`http://localhost:8750/`. `smoke`: `["python","-m","v5.smoke"]`. smoke = probe, then run 1 "My client is 55,
retiring at 62", run 2 "How many years left?" with the same session (and prev id). Assert the reply has a 7
(digit or "seven"), `restored` true, and both executionIds found by `search_by_correlation`.
It prints the memorySource/agentMode used.
